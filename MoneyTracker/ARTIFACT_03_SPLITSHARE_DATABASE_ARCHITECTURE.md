# ARTIFACT 03 — DATABASE ARCHITECTURE, SCHEMA & DATA DICTIONARY
## SplitShare / Collaborative Finance Tracker

**Status:** Database source of truth for MVP implementation  
**Depends on:**  
- `ARTIFACT 01 — PRODUCT FOUNDATION, WORKFLOWS & EDGE CASES`
- `ARTIFACT 02 — TECHNICAL ARCHITECTURE & STACK`

**Database:** PostgreSQL  
**ORM:** SQLAlchemy 2.x

This document defines the authoritative database design for SplitShare.

It exists to make implementation predictable for Codex and future developers by specifying:

- all MVP tables;
- all IDs;
- all foreign keys;
- all timestamps;
- all status fields;
- all lifecycle fields;
- all financial columns;
- all unique constraints;
- all check constraints;
- all indexes;
- soft-delete behavior;
- concurrency/version fields;
- idempotency records;
- audit/activity records;
- relationship rules;
- financial integrity rules;
- deletion behavior;
- future extension boundaries.

This artifact must be treated as the database source of truth unless a later migration artifact explicitly changes the schema.

# 2. DATABASE DESIGN PRINCIPLES

## 2.1 Every Major Record Has an ID

Every persisted business entity must have a stable primary ID.

Use:

```text
UUID
```

for all primary keys.

Do not use:

- auto-increment integer IDs as the public identity;
- email addresses as primary keys;
- composite primary keys for core entities;
- user-visible names as identifiers.

---

## 2.2 Timestamp Naming Standard

The canonical timestamp names are:

```text
created_at
updated_at
deleted_at
```

`updated_at` is the standard replacement for names such as:

```text
modify_at
modified_at
last_modified_at
```

Do not create both `modify_at` and `updated_at`.

Use `updated_at` everywhere.

Additional lifecycle timestamps are allowed and required where the domain needs them:

```text
joined_at
removed_at
accepted_at
declined_at
revoked_at
expires_at
settled_at
last_used_at
revoked_at
completed_at
```

All timestamps representing a moment must use:

```text
TIMESTAMPTZ
```

and be stored in UTC.

Business-only calendar dates such as an expense date use:

```text
DATE
```

because they represent a chosen date, not a precise timestamp.

---

# 3. GLOBAL COLUMN CONVENTIONS

## 3.1 Primary Key

Every major table:

```text
id UUID PRIMARY KEY
```

IDs should be generated by the application or database using one consistent UUID strategy.

---

## 3.2 Creation Audit

For business records where a human user creates the record:

```text
created_by UUID NULL
created_at TIMESTAMPTZ NOT NULL
```

`created_by` may be nullable for system-generated records.

---

## 3.3 Update Audit

For mutable business records:

```text
updated_by UUID NULL
updated_at TIMESTAMPTZ NOT NULL
```

`updated_at` must change whenever persisted business state changes.

---

## 3.4 Soft Delete

For entities requiring historical accountability:

```text
deleted_at TIMESTAMPTZ NULL
deleted_by UUID NULL
```

A row is active when:

```text
deleted_at IS NULL
```

Soft deletion is required for financial records.

---

## 3.5 Optimistic Concurrency

Mutable financial/business records use:

```text
version INTEGER NOT NULL DEFAULT 1
```

Every successful update increments:

```text
version = version + 1
```

Clients must submit the version they edited.

A stale version must be rejected.

---

# 4. MONEY STORAGE

Never use PostgreSQL floating-point types for authoritative money.

Use:

```text
BIGINT
```

representing minor currency units.

Examples:

```text
PHP ₱1,250.50
→ 125050

USD $45.00
→ 4500

JPY ¥1000
→ 1000
```

Canonical column suffix:

```text
_amount_minor
```

Examples:

```text
amount_minor
old_amount_minor
new_amount_minor
```

Tracker defines:

```text
currency_code
currency_exponent
```

# 6. USERS TABLE

## 6.1 Purpose

Stores global user identity.

A user exists independently from trackers.

## 6.2 Schema

```text
users
-----
id                  UUID            PK
email               VARCHAR(320)    NOT NULL
email_normalized    VARCHAR(320)    NOT NULL
name                VARCHAR(150)    NOT NULL
password_hash       VARCHAR(255)    NOT NULL
avatar_url          TEXT            NULL
status              VARCHAR(30)     NOT NULL DEFAULT 'active'

email_verified_at   TIMESTAMPTZ     NULL

last_login_at       TIMESTAMPTZ     NULL

created_at          TIMESTAMPTZ     NOT NULL
updated_at          TIMESTAMPTZ     NOT NULL
deleted_at          TIMESTAMPTZ     NULL
```

## 6.3 Status Values

Recommended:

```text
active
suspended
deleted
```

## 6.4 Constraints

```text
UNIQUE(email_normalized)
```

`email_normalized` should contain canonical lowercase/trimmed email representation.

## 6.5 Indexes

```text
idx_users_email_normalized
idx_users_status
idx_users_deleted_at
```

## 6.6 Notes

Do not cascade-delete financial records when a user is deleted.

Historical expenses and settlements may continue referencing the user.


## 8.3 Status Values

```text
active

deleted
```

## 8.4 Constraints

```text

```


Every active Tracker must have exactly one Owner.

```text

```

## 9.2 Schema

```text

updated_at          TIMESTAMPTZ     NOT NULL
```

## 9.3 Role Values

```text
owner
editor
commenter
viewer
```

## 9.4 Status Values

```text
active
removed
```

## 9.5 Constraints

At minimum:

```text
role IN ('owner', 'editor', 'commenter', 'viewer')
status IN ('active', 'removed')
```

A removed member must have:

```text
removed_at IS NOT NULL
```

An active member should have:

```text
removed_at IS NULL
```

## 9.6 Unique Active Membership

There must be only one active membership per:

```text
(tracker_id, user_id)
```

Recommended partial unique index:

```text
UNIQUE(tracker_id, user_id)
WHERE status = 'active'
```

## 9.7 Owner Uniqueness

Recommended partial unique index:

```text
UNIQUE(tracker_id)
WHERE role = 'owner'
  AND status = 'active'
```

## 9.8 Indexes

```text
idx_tracker_members_tracker_id
idx_tracker_members_user_id
idx_tracker_members_tracker_user
idx_tracker_members_role

```

# 12. EXPENSES TABLE

## 12.1 Purpose

Represents an expense paid by one Tracker member.

## 12.2 Schema

```text
expenses
--------
id                  UUID            PK

tracker_id          UUID            NOT NULL FK trackers(id)

description         VARCHAR(255)    NOT NULL
amount_minor        BIGINT          NOT NULL
```

## 12.3 Constraints

```text
amount_minor > 0
version >= 1
CHAR_LENGTH(TRIM(description)) > 0
```

## 12.4 Financial Rules

The expense must have at least one split.

The sum of active splits must equal:

```text
expenses.amount_minor
```

This cross-row invariant is enforced transactionally in application logic and verified by tests.

## 12.5 Indexes

```text

```


## 13.1 Purpose

Stores each participating member's assigned share of one Expense.

## 13.2 Schema

```text
expense_splits
--------------
id                  UUID            PK

expense_id          UUID            NOT NULL FK expenses(id)
user_id             UUID            NOT NULL FK users(id)

amount_minor        BIGINT          NOT NULL

created_at          TIMESTAMPTZ     NOT NULL

```

## 13.3 Constraints

```text

```

## 13.4 Notes

Do not add:

```text

```

to normal split records unless future requirements require independent split deletion.

For expense edit, split rows should be replaced or updated inside the same database transaction as the parent Expense.

The parent Expense soft-delete controls whether splits affect balances.


# 14. SETTLEMENTS TABLE

## 14.1 Purpose

Records money paid from one Tracker member to another to reduce outstanding debt.

A Settlement records an external payment.

The application does not transfer money in MVP.

## 14.2 Schema

```text
settlements
-----------
id                  UUID            PK

tracker_id          UUID            NOT NULL FK trackers(id)

from_user_id        UUID            NOT NULL FK users(id)
to_user_id          UUID            NOT NULL FK users(id)

amount_minor        BIGINT          NOT NULL

settlement_date     DATE            NOT NULL

version             INTEGER         NOT NULL DEFAULT 1

created_by          UUID            NOT NULL FK users(id)
updated_by          UUID            NULL FK users(id)
deleted_by          UUID            NULL FK users(id)

created_at          TIMESTAMPTZ     NOT NULL
updated_at          TIMESTAMPTZ     NOT NULL
deleted_at          TIMESTAMPTZ     NULL
```

## 14.3 Constraints

```text
amount_minor > 0
from_user_id <> to_user_id
version >= 1
```

## 14.4 MVP Overpayment Rule

Before insert, backend must verify:

```text
amount_minor <= current direct outstanding debt
```

between:

```text
from_user_id → to_user_id
```

## 14.5 Indexes

```text
idx_settlements_tracker_id
idx_settlements_from_user_id
idx_settlements_to_user_id
idx_settlements_tracker_pair
idx_settlements_settlement_date
idx_settlements_deleted_at
```

Recommended pair index:

```text
(tracker_id, from_user_id, to_user_id)
WHERE deleted_at IS NULL
```

# 21. FOREIGN KEY DELETION POLICY

Do not use uncontrolled cascading deletes for core financial history.

Recommended behavior:

## users

Historical financial references:

```text
ON DELETE RESTRICT
```

or account soft deletion.

## trackers

Because tracker deletion is soft-delete in product behavior:

```text
ON DELETE RESTRICT
```

for child financial records.

## expenses → expense_splits

If a physical expense row were ever permanently removed in controlled maintenance:

```text
ON DELETE CASCADE
```

for `expense_splits` may be acceptable.

Normal application behavior must still soft-delete the Expense instead of physically deleting it.

## comments

A future physical expense purge may cascade comments if retention policy explicitly allows it.

# 24. BALANCE CALCULATION SOURCE TABLES

Current balances are derived from:

```text
expenses
expense_splits
settlements
```

Do not create:

```text
tracker_members.balance
users.balance
trackers.balance
```

as authoritative values.

---

# 25. MEMBER BALANCE FORMULA

For one user inside one Tracker:

```text
balance_minor =
    SUM(active expenses paid by user)
  - SUM(active splits assigned to user)
  + SUM(active settlements sent by user)
  - SUM(active settlements received by user)
```

Interpretation:

```text
> 0  → user is owed
< 0  → user owes
= 0  → settled
```

---

# 26. TRACKER ZERO-SUM INVARIANT

For a valid shared-expense tracker:

```text
SUM(all member balances) = 0
```

This must remain true:

- after expense creation;
- after expense edit;
- after expense deletion;
- after settlement creation;
- after settlement edit;
- after settlement deletion.

Automated tests should enforce this invariant.

---

# 27. PAIRWISE DEBT DATA STRATEGY

Do not store pairwise debt as an independently editable table in MVP.

Pairwise debt should be derived from financial history.

Avoid:

```text
member_debts
-----------
from_user
to_user
amount
```

as source of truth.

If future performance requires a projection/cache table, it must be rebuildable.

---

# 28. WHY BALANCES ARE NOT STORED DIRECTLY

Direct balance columns create synchronization risk.

Example:

```text
Expense changes
but balance update fails
```

Then the database contains contradictory financial truth.

Therefore:

```text
Expenses + Splits + Settlements
```

are authoritative.

Balance summaries are calculated read models.

---

# 29. EXPENSE CREATION TRANSACTION

Expense creation must be one PostgreSQL transaction.

Sequence:

```text
BEGIN

1. validate tracker
2. validate actor membership
3. validate actor role
4. validate payer
5. validate participant members
6. calculate equal splits
7. INSERT expense
8. INSERT expense_splits
9. verify split sum
10. INSERT activity_log

COMMIT
```

Any failure:

```text
ROLLBACK
```

---

# 30. EXPENSE UPDATE TRANSACTION

```text
BEGIN

1. validate authorization
2. load expense
3. verify deleted_at IS NULL
4. verify expected version
5. validate new payer/participants
6. calculate new splits
7. UPDATE expense
8. replace/update splits
9. verify sum
10. increment version
11. INSERT activity_log

COMMIT
```

Stale version:

```text
ROLLBACK
409 Conflict
```

---

# 31. EXPENSE DELETE TRANSACTION

```text
BEGIN

1. authorize
2. validate expense active
3. SET deleted_at = NOW()
4. SET deleted_by = actor
5. increment version
6. INSERT activity_log

COMMIT
```

Do not physically delete `expense_splits`.

They remain historical children of the soft-deleted Expense.

Balance query excludes the deleted Expense and therefore its splits.

---

# 32. SETTLEMENT CREATION TRANSACTION

```text
BEGIN

1. authorize
2. validate from_user
3. validate to_user
4. calculate current direct obligation
5. verify amount > 0
6. verify amount <= outstanding
7. INSERT settlement
8. INSERT activity_log

COMMIT
```

Outstanding amount must be recalculated inside the transaction.

---

# 33. OWNERSHIP TRANSFER TRANSACTION

```text
BEGIN

1. verify actor is current owner
2. verify target member active
3. update previous owner membership → editor
4. update target member membership → owner
5. update trackers.owner_user_id
6. increment tracker.version
7. INSERT activity_log

COMMIT
```

Database constraints must prevent two active owners.

---

# 34. MEMBER REMOVAL

Member removal does not erase history.

Update:

```text
status = 'removed'
removed_at = NOW()
removed_by = actor
updated_at = NOW()
```

Historical rows remain referenced by:

- expenses;
- splits;
- settlements;
- activity.

Do not null these user references.

# 38. ENUM STRATEGY

Recommended MVP approach:

Use constrained `VARCHAR` values through:

- application enums;
- database check constraints.

This provides flexibility for migrations while still preventing invalid values.

Example:

```text
role VARCHAR(30)
CHECK role IN ('owner', 'editor', 'commenter', 'viewer')
```

Do not allow arbitrary role strings.

---

# 39. NULLABILITY RULES

General rule:

Use `NOT NULL` when absence would make the row ambiguous or invalid.

Examples that must be NOT NULL:

```text
users.email
trackers.name
trackers.currency_code
tracker_members.role
expenses.amount_minor
expenses.paid_by_user_id
expense_splits.amount_minor
settlements.amount_minor
activity_logs.action
```

Use NULL only where “not yet happened” or “optional” is meaningful.

Examples:

```text
deleted_at
removed_at
accepted_at
revoked_at
note
avatar_url
```

---

# 40. DEFAULT VALUE RULES

Database defaults should be predictable.

Examples:

```text
version = 1
status = 'active'
metadata = '{}'
is_system = FALSE
is_active = TRUE
```

Timestamps may use server/database defaults for `created_at`, but application and database behavior must remain consistent.

---

# 41. UPDATED_AT POLICY

Every mutable table must update:

```text
updated_at
```

when persisted fields change.

Recommended implementation:

- set `updated_at` in application/ORM update logic;
- optionally add a database trigger as a safety net only if the team intentionally adopts trigger-based timestamp management.

Do not mix inconsistent strategies table-by-table.

---

# 42. SOFT DELETE QUERY POLICY

All repository queries must explicitly define whether they load:

```text
active only
historical only
all
```

Default user-facing queries should use:

```text
deleted_at IS NULL
```

Financial balance calculations must exclude:

```text
expenses.deleted_at IS NOT NULL
settlements.deleted_at IS NOT NULL
```

---

# 43. ACTIVITY LOG RETENTION

Activity logs should generally not be deleted when:

- an expense is deleted;
- a settlement is corrected;
- a member leaves;
- a Tracker record is renamed.

The activity row preserves historical context.

---

# 44. DATA ACCESS SECURITY

Every Tracker-scoped read/write must verify:

```text
tracker_members.tracker_id
tracker_members.user_id
tracker_members.status = 'active'
```

before returning protected tracker data.

Never rely on knowing a UUID as authorization.

# 45. QUERY: USER'S TRACKERS

Conceptually:

```sql
SELECT ...
FROM trackers t
JOIN tracker_members tm
  ON tm.tracker_id = t.id
WHERE tm.user_id = :current_user_id
  AND tm.status = 'active'
  AND t.deleted_at IS NULL;
```

This is the base security scope for the Trackers list.

# 46. QUERY: ACTIVE TRACKER EXPENSES

# 56. STATUS + TIMESTAMP CONSISTENCY


```text

```

Example refresh session:

```text

```

Application services must update them atomically.

# 57. DATABASE TRANSACTION ISOLATION EXPECTATION

Use PostgreSQL transactions for all multi-record financial changes.

Operations that validate a current obligation before inserting a settlement must be protected against concurrent changes using appropriate locking/version revalidation.

Exact isolation/locking implementation belongs to code, but product invariant is:

> A settlement may not commit against an amount that was already invalidated by a concurrent financial change.

# 62. REQUIRED DATABASE TESTS

## Membership

- duplicate active membership rejected;

# 74. REQUIRED TIMESTAMP RULES FOR CODEX

Codex must obey:

1. Use `created_at`, never `create_at`.
2. Use `updated_at`, never `modify_at`.
3. Use `deleted_at` for soft-deleted financial records.
4. Use `joined_at` for actual membership start.
5. Use `removed_at` for membership removal.
6. Use `expires_at` for expiring sessions/invites/tokens.
7. Use `accepted_at` when invitation is accepted.
8. Use `declined_at` when invitation is declined.
9. Use `revoked_at` when invitation/session/token is revoked.
10. Use `last_used_at` for refresh-session usage.
11. Use `last_login_at` on user login.
12. Use `password_changed_at` after password update.
13. Use `email_verified_at` if email verification exists.
14. Use `completed_at` when asynchronous/idempotent operation lifecycle needs completion time.
15. Use `DATE` for `expense_date` and `settlement_date`.
16. Use UTC `TIMESTAMPTZ` for actual event timestamps.
17. Never store local-time-only timestamps as authoritative event times.

---

# 75. REQUIRED ID RULES FOR CODEX

1. Every main business table gets `id UUID PRIMARY KEY`.
2. Foreign keys use `<entity>_id`.
3. Actor references use:
   - `created_by`
   - `updated_by`
   - `deleted_by`
   - or domain-specific names such as `invited_by`.
4. Never infer relationships from email/name.
5. Never expose database identity through sequential enumeration.
6. Never reuse a deleted entity's ID for a new entity.
7. IDs remain stable even if display names change.

---

# 76. REQUIRED MONEY RULES FOR CODEX

1. Use `BIGINT` minor units.
2. Never store authoritative money as float.
3. Expense total must equal split sum.
4. Deleted Expenses do not affect balances.
5. Deleted Settlements do not affect balances.
6. Balances are derived.
7. Client-provided balance values are ignored.
8. Settlement amount is revalidated server-side.
9. Equal-split remainder distribution is deterministic.
10. All financial-changing operations are transactional.

---

# 77. REQUIRED DATABASE RULES FOR CODEX

1. PostgreSQL is the production database.
2. SQLAlchemy 2.x models must match this schema.
3. Alembic owns schema changes.
4. Do not manually change production schema.
5. Use UUID primary keys.
6. Use UTC `TIMESTAMPTZ`.
7. Use `updated_at` as canonical modification timestamp.
8. Use soft deletion for financial history.
9. Use foreign-key constraints.
10. Use unique constraints for identity invariants.
11. Use check constraints for simple valid-state invariants.
12. Use indexes based on real query paths.
13. Do not add cached balance tables to MVP.
14. Do not add future feature tables without promoted requirements.
15. Do not cascade-delete financial history from user deletion.
16. Do not create two active owners.
17. Do not create duplicate active tracker memberships.
18. Do not create duplicate participant rows per Expense.
19. Do not accept duplicate sensitive writes without idempotency protection.
20. Do not allow stale financial updates to overwrite current data.

# 78. MVP DATABASE DEFINITION OF DONE

The database is ready for MVP only when:

## Schema

- all required tables exist;
- all PKs are UUID;
- all FKs are valid;
- all required timestamps exist;
- money uses BIGINT minor units;
- version fields exist where required.

## Integrity

- one active owner per Tracker;
- one active membership per user/Tracker;
- split participants unique;
- positive expenses enforced;
- positive settlements enforced;
- self-settlement blocked;
- invitation states valid.

## Financial

- split total equals Expense total;
- balances reconstruct correctly;
- deleted Expenses are ignored;
- deleted Settlements are ignored;
- settlements cannot overpay;
- tracker balances remain zero-sum.

## Audit

- Expense changes have actor/timestamps;
- Settlement changes have actor/timestamps;
- Tracker changes have actor/timestamps;
- member lifecycle timestamps are preserved;
- Activity Logs represent important actions.

## Reliability

- idempotency works;
- stale writes are rejected;
- migrations run from empty database;
- migrations upgrade an existing database;
- rollback behavior is tested;
- restore procedure is documented.

# 79. FINAL DATABASE CONTRACT

The SplitShare database must preserve enough information to answer:

> **Who created it?**  
> **Who changed it?**  
> **When was it created?**  
> **When was it changed?**  
> **Was it deleted?**  
> **Who paid?**  
> **Who participated?**  
> **How much was each person's share?**  
> **Who settled with whom?**  
> **When did that settlement happen?**  
> **What is the current balance, and can it be reconstructed from history?**

No financial state should exist only as a UI value or manually edited balance field.

The authoritative financial history is:

```text
Expenses
+ Expense Splits
+ Settlements
```

The authoritative collaboration/access history is:

```text
Tracker Membership
+ Invitations
+ Activity Logs
```

The authoritative identity/session layer is:

```text
Users
+ Refresh Sessions
```

This schema is the database foundation for the SplitShare MVP.
